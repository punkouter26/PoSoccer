# ML-Agents audit — 2026-09-13

Scope as asked: training configs, reward shaping, observation spaces, non-essential
agent logic, ragdoll joint limits/collisions, bio-realistic locomotion, and training
throughput on this host. Adjustments staged, **no training executed**.

This is the second pass of its kind; `docs/ml-audit-2026-09-07.md` is the first, and
much of what that one cleared is still cleared — see "Not re-litigated" at the end.
Where this pass **contradicts** it, that is called out rather than quietly corrected.

**A run was live throughout: `soccer_p27gain_matt`**, started 15:35, 4 env processes +
trainer, at 700k/10M when measured. Nothing here touched it, and two staged changes
were deliberately withheld because of it (see §10).

---

## Headline: the throughput bottleneck is the trainer, and the machine is 83% idle

Sampled over 20 s against the live run, `TotalProcessorTime` deltas divided by wall:

| process | cores | of 12 logical | working set |
|---|---|---|---|
| trainer (`python` 30176) | **1.00** | 8.3% | 1304 MB |
| `PoSoccer.exe` ×4 | 0.17–0.21 each | 1.4–1.7% each | ~218 MB each |
| **total** | **~2.1** | **~17%** | |
| system-wide CPU | | **40%** | (three Unity editors included) |
| GPU | | **27%** | (three Unity editors included) |

The trainer is pegged at **exactly one core** — single-threaded — while each of the
four Unity env players sits at **a fifth of a core**, waiting.

**This reverses the premise the 2026-09-07 audit reasoned from.** That pass rejected
`Physics2DSettings.useMultithreading` on the grounds that per-process physics workers
"would contend for cores that are already saturated". The rejection is still correct,
but not for that reason — the cores are not saturated, the envs are idle, and physics
is not the constraint. The consequence is larger than one setting: **every env-side
throughput lever in that document is optimising the cheap half of a pipeline that is
already waiting.** `m_VelocityIterations`, `m_QueriesStartInColliders`, continuous
collision detection — all of them buy back time the envs are not spending.

Corroborating arithmetic from the same run: **700,000 steps in 483.5 s** across 4 envs
× 16 pitches = 64 trainer-facing agents → 10,937 decisions/agent → ×8 physics ticks at
0.01 s = an **effective time scale of ~1.8×** against a configured `time_scale: 20`.
The player delivers under a tenth of what the config asks for. That number is a
ceiling, not a throttle; raising it buys nothing.

**The trainer's one thread does two things**: gradient updates (GPU, only 27% busy for
a 256×2 MLP) and the gRPC/protobuf round-trip of every observation. **178 floats × 64
agents, 12.5 times per simulated second.** That makes the observation payload a
first-class throughput term, which is why §1 below is both the modelling idea and the
throughput idea.

## The ten, ranked by expected value

### 1. Cut the ray battery — it is 120 of 178 inputs and near-pure redundancy

`Sensor_Vision` fires **40 spherecasts per agent per decision** across four sensors,
producing 120 of the 178 model inputs (67.4%). What they carry is already in the vector
observation **exactly, unbounded, and in body frame**: ball relative position and
velocity, both goal positions, the two nearest opponents' positions and velocities. The
rays' only unique contribution is **occlusion** — and in a top-down 1v1 with two circular
bodies and four straight walls, there is nearly none to carry.

The previous audit reached the same doorstep and stopped ("that is the experiment to
run, deliberately, after the reward work settles"). The new measurement is what makes it
the top item rather than a tidy-up: the payload is what the bottleneck process chews on,
so this is simultaneously the largest modelling simplification and the largest throughput
win available.

Staged order, each its own single-variable run:

| step | drop | inputs | casts/agent | rationale |
|---|---|---|---|---|
| a | `Sensor_Goal` + `Sensor_Walls` | 178 → 136 | 40 → 26 | most redundant; walls are 12 u on a pitch whose nearest wall is 18 u from centre — an 18.5% blind rectangle the previous audit measured |
| b | + `Sensor_Ball` + `Sensor_Opponents` | 136 → 58 | 26 → 0 | replace with 4 analytic wall-distance floats; **58 inputs, zero casts** |

**Not applied.** It changes the observation contract, which obsoletes the deployed
`STANDARD.onnx` and would land while p27 has yet to export MATT. See §10.

### 2. Stop building observations the scripted opponent throws away — **applied**

ML-Agents does **not** skip perception for a heuristic agent. `Agent.SendInfoToBrain`
calls `UpdateSensors()` unconditionally — which is where `RayPerceptionSensor.Update()`
fires every cast — and then `HeuristicPolicy.RequestDecision` calls `StepSensors`, which
writes each sensor into a `NullList` whose `Add` is an empty method. Verified in the
embedded package at `Runtime/Policies/HeuristicPolicy.cs:35` and `Agent.cs:1150`.

So in every phase-1 run the scripted RED agent casts its full 40-ray battery and runs
`CollectObservations` at 12.5 Hz, and **all of it is discarded**. Across 4 processes ×
16 pitches that is 64 agents — **half the perception in the run** — computed for nothing.

`Agent_HeuristicBot.ComputeActions` reads transforms and rigidbodies directly and
consults no sensor, so the learner faces a bit-identical opponent. `Sensor_Vision.Awake`
now skips the battery for that side, behind `Agent_Soccer.IsSensorlessScriptedSide`.
Three exclusions carry the whole contract, and each is a case where a heuristic agent's
observations genuinely *are* read: a demo-recording run (`POSOCCER_RECORD_DEMO`, whose
entire product is the bot's observation/action pairs), self-play (RED is on the trainer),
and any match or menu scene.

### 3. `threaded: true` — the one config lever that aims at the measured bottleneck

`TrainerSettings.threaded` defaults to `False` (`settings.py:639`) and every config this
project has ever run inherited it. It serialises the loop: step every env, **then** run
the gradient update with all four env processes blocked. That is exactly the shape of
the table above. Staged as `config/TRAIN_STANDARD_p28.yaml`, learning config byte-
identical to p22 (the last **graded** configuration, 26.6% at n=350).

**The honest cost**, since this is easy to present as free: overlap means some
trajectories are collected under a policy one update behind the one being optimised.
PPO is on-policy; that is a small, real staleness bounded by one update. Hence a
single-variable run against a graded baseline, not a default flipped into 18 configs.

Judge it on **s/M steps** off the checkpoint timestamps (p22's baseline is 642.2 s/M
over nine 1M intervals, 637–658), then confirm the grade lands inside ±4.7 pp of 26.6%.

### 4. Gate the three presentation roots out of headless runs — **applied**

`Agent_Audio` has bailed on `-batchmode -nographics` since the crowd bed was caught
droning under four env processes, and `Agent_Soccer.Start` skips cosmetics the same way.
**The three components serialized on the `SCN_Training` root never got the check.**
`SCN_Training` serializes `showHud: 1`, so every headless env process built the full
scoreboard — bands, chips, clock, toast, win-probability strip — and ran its `Update()`
every frame. `Agent_Stadium.Awake` additionally sweeps
`FindObjectsByType<SpriteRenderer>()` across a scene `Agent_TrainingGrid` has cloned into
sixteen pitches, to assign a lit material to renderers that are never rendered.
`Agent_MatchFX` is worse than wasteful: its shake writes `Camera.main.transform` and its
squash writes a `Transform` scale, inside a run whose numbers the benchmark depends on.

The condition now lives once, as `Agent_Presentation.IsHeadless`, and `Agent_Audio` was
refactored onto it so there is one definition rather than four copies that can drift. It
is deliberately **separate** from `IsMatchScene`: that gate asks "is a human watching
this scene", this one asks "does this process have a screen". Conflating them would have
gated the eval path, which runs headless but is not a match scene.

### 5. The personalities lost a differentiating trait, silently, to a form change

`useDifferentialBallToGoal` is `true` on all five profiles, so `ApplyDenseRewards` takes
the potential-based branch and **`ballToGoalVelocityScale` is inert**. But it is still
carrying per-personality values that read as deliberately tuned:

| profile | `ballToGoalVelocityScale` (inert) | `ballToGoalProgressScale` (live) |
|---|---|---|
| STANDARD | 0.0001 | 0.02 |
| MATT (striker) | **0.00011** | 0.02 |
| NICK (midfielder) | **0.00004** | 0.02 |
| KIM (wall) | **0.00006** | 0.02 |

MATT was paid ~2.75× NICK on the goalward axis. He is now paid **identically**. The v6
change (2026-09-07) converted the term from a velocity rate to a potential and gave the
new coefficient one value everywhere; the old per-personality spread was left in the
asset, still readable, no longer connected to anything. A striker and a midfielder that
share every coefficient on the axis that distinguishes them are not two personalities.

Proposed (not applied — see §10): carry the ratio across as
`ballToGoalProgressScale` ≈ MATT 0.022 / STANDARD 0.02 / KIM 0.012 / NICK 0.008, and
**delete** `ballToGoalVelocityScale` from the assets rather than leave an inert field
that reads as tuned. A number that looks set and does nothing is how this one was lost.

### 6. The two signature trait terms were invisible to the reward accounting — **applied**

`_rewardAccounting` streams each dense term to TensorBoard as `Reward/<name>` precisely
so nobody has to re-derive ceilings by inference. Eight terms went through `Account`.
**The two that did not were `defensivePositionScale` and `possessionScale`** — KIM's and
NICK's signature terms, the single coefficient that makes each of them a distinct player.
They called `AddReward` directly, so a KIM run's board showed seven terms summing to less
than her realized dense reward with nothing naming the difference. `TermCount` 8 → 10,
`TermNames` gains `defense` and `possession`.

### 7. Dead per-step math in the reward path — **applied**

`facingAlignmentScale` and `crossbarProximity` are **0 on all five shipped profiles**
(both retired 2026-09-07). The code computed them anyway, on every agent, on every
physics step:

- `float align = Vector2.Dot(transform.up, toBall.normalized)` — a normalize + dot,
  multiplied by zero.
- `float progress = …` — computed unconditionally *above* the crossbar block under a
  comment reading "retained for the crossbar term below", a second normalize + dot for a
  branch that never executes. It now lives inside the guard, which is the only place it
  was ever read.

Both guarded rather than deleted: they remain legal A/B levers.

### 8. Physics and collision settings — proposals, explicitly *not* applied

Now demoted, because §Headline shows the envs are idle. Recorded so the next pass does
not spend a pilot on them before the trainer ceiling is lifted:

- `m_VelocityIterations` 8→6, `m_PositionIterations` 3→2.
- `m_QueriesStartInColliders: 1` → 0 (every ray currently starts inside the caster's own
  collider).
- Agents are `m_CollisionDetection: 1` (Continuous). At 0.01 s and ~10 m/s peak they
  travel 0.1 m/tick against a 0.8 m diameter — CCD can never trigger. **The ball must
  stay Continuous**: 14 m/s (the wall-kick pop) is 0.14 m/tick against a 0.22 m diameter.

All three alter contact dynamics, so each needs its own pilot. `useMultithreading` stays
off — now for the *correct* reason, plus the `useConsistencySorting: 0` determinism cost.

### 9. There is no ragdoll to tune, and the locomotion model is already sound

Asked for, so answered explicitly rather than skipped:

- **Joint limits / collisions:** there is nothing to tune. Each player is a single
  `Rigidbody2D` — no articulation, no joints. Recorded as an open deviation in
  `docs/rules-exemptions.md` §2, deferred because per-joint state and drive targets
  change both the observation and action spaces and obsolete every `.onnx`.
- **Bio-realistic locomotion:** already thorough within that constraint — one friction
  circle of `mu·m·g` shared by launching, cutting and braking; active foot braking out of
  spare traction; anisotropic drag so strafing is ~64% of running; turn authority falling
  to 25% at sprint; force slew; mass-scaled drive; contact-based drive authority.
- One hypothesis was **checked and is wrong**: that the measured 174° heading churn came
  from undamped rotation. `m_AngularDamping` is **5** on both agents in `SCN_Training`
  (and 0.5 on the ball). Spin decays correctly; churn is a policy property, not a physics
  one. Recorded because it is a cheap wrong turn to take twice.

### 10. Two things were withheld on purpose, and the reason is the live run

`soccer_p27gain_matt` is mid-flight and has not exported. Both withheld changes would
land underneath it:

- **The ray-battery cut (§1)** changes the observation contract. It obsoletes the
  deployed `STANDARD.onnx`, fails `Agent_EditMode_ObsContract`, and would make p27's
  MATT export unloadable against the runtime that produced it.
- **The personality re-differentiation (§5)** rewrites `Reward_MATT.asset` — the reward
  table of a run that is currently training against it. The run would finish under a
  config that no longer describes it, which is precisely the incomparability this project
  has documented twice (the p18→p20 `stepPenalty` step, and the 2026-08-28 frame change).

Neither is blocked on judgement; both are blocked on p27 landing.
